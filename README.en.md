# Hackintosh EFI Audit Tool

Guided OpenCore setup and EFI auditing for **Intel hackintosh laptops and desktops** — pick the right MacBook SMBIOS with a three-axis rule, gather every hardware fact step by step, audit tool-generated EFIs, verify SSDTs against your machine's own DSDT, and finish with power management and per-peripheral acceptance checks.

> **Core principle:** pick the model first (iGPU generation + TDP class + macOS version eligibility), then derive the config from the model. Pick the wrong SMBIOS and every kext and patch afterwards is a house built on the wrong foundation.
>
> **Second principle:** tool output is untrusted by default. [OpCore-Simplify](https://github.com/corpnewt/OpCore-Simplify) is an excellent collector and accelerator, but it does not filter by macOS version eligibility (axis 3) and cannot see your BIOS state or your machine's DSDT. From 10th-gen onward, iGPU generation decouples from CPU generation — any "map by CPU generation" output must be manually reviewed.

## What it covers

- **Three-axis SMBIOS selection** — iGPU generation × TDP class × macOS version eligibility (Tahoe only supports 16,1/16,2/16,4), with the four most widespread community misconceptions corrected (e.g. **MacBookPro16,2 = Ice Lake/Gen11, Tahoe ✅; 16,3 = Coffee Lake-U/Gen9.5, Tahoe ❌** — and 10th-gen Comet Lake-U laptops have no native Apple counterpart at all).
- **Guided 7-phase workflow** — environment determination → hardware intake (5 batches, ≤ 4 questions per round, each with "how to find the answer") → model selection → SSDT audit → power management quad (pmset / CPUFriend / CFG-Lock / DVMT) → peripheral acceptance → regression checks. Progress is written to a checklist file so sessions can resume across restarts.
- **OpCore-Simplify output review** — static audit of `Report.json` + ACPI folder + `config.plist` **before the machine can even boot macOS**: three-axis re-check, iGPU properties, quirk risks, whether the dGPU is truly disabled, kext redundancy, SSDT reference paths, USB mapping TODOs. Auto-detects the two 2026 experimental GPU routes and flags config-level conflicts such as **WhateverGreen + WhateverXe enabled together**.
- **SSDT precision audit** — every generic SSDT checked against your machine's DSDT (EC/EC-USBX, PLUG, PNLF, GPI0/XOSI, AWAC, dGPU `_OFF`, HPET/`_PRW`), with the classic laptop traps for each.
- **Experimental hardware routes** — NVIDIA Turing+ dGPUs (NullMoth, Sequoia only) and 11th/12th-gen Xe-LP iGPUs (WhateverXe / NootedGreen): selection criteria, prerequisites, troubleshooting. Experimental ≠ stable; these exist for people who already own the hardware.
- **Desktop platforms** — iMac / Mac mini / Mac Pro model selection and EFI auditing (laptop-specific checks are auto-skipped/downgraded). AMD CPU platforms are out of scope.

## How to use it

Send any of these to your AI assistant with the skill installed:

1. **Review an OpCore-Simplify result** — "Review the EFI generated by opcore-simplify: here's Report.json, the ACPI folder and config.plist." → `scripts/audit_opcore_result.py`
2. **Choose a spoof model** — "My laptop is an i7-10510U with UHD620 and I want macOS Ventura — which MacBook model and board-id should I use?" → `scripts/recommend_smbios.py`
3. **Audit an existing EFI** — "Here's my config.plist, audit it item by item." → `scripts/efi_config_audit.py` (✅/⚠️/❌ graded findings, platform-aware)
4. **Fresh install or symptom troubleshooting** — "Help me troubleshoot lid-sleep crashes / no iGPU acceleration / fast battery drain / silent microphone."
5. **Collect hardware facts cross-platform** — read-only commands for Windows / macOS / Linux → `scripts/collect_hw.py`

All scripts depend only on the **Python standard library** and run on Windows, macOS and Linux. Both audit scripts support `--json` (machine-readable findings, exit 0/2) and **automatically invoke `ocvalidate`** at the end when it can be found (explicitly reported, never silently skipped).

## Anti-patterns this skill enforces against

- ❌ Copying someone else's EFI for the "same" laptop (serials must be self-generated; SSDTs must match your DSDT)
- ❌ Trusting a tool's model pick without three-axis review (10th-gen U-series breaks axes 1–2; target Tahoe requires axis 3)
- ❌ Ignoring macOS version eligibility — Tahoe only supports 16,1/16,2/16,4; everything else stops at Sequoia
- ❌ Blindly raising `framebuffer-stolenmem` for "performance" (no benefit; too large causes boot panics)
- ❌ Hand-crafting CPUFriend data ported from another machine (measured: stuck at low frequency after wake, no turbo)
- ❌ Putting `layout-id` in boot-args (AppleALC only reads DeviceProperties)
- ❌ Expecting an Optimus dGPU to accelerate the internal display (physically separate paths, no mux)
- ❌ Relying on CFG-Lock quirks long-term instead of unlocking the BIOS
- ❌ Treating NullMoth / WhateverXe / NootedGreen as stable daily-driver solutions
- ❌ Enabling WhateverGreen and WhateverXe at the same time (documented as mutually exclusive — a config error)

## Safety discipline (read before touching the ESP)

1. **Never hardcode disk numbers** — they drift. Use the volume UUID or look up `diskutil list | grep "EFI EFI"` at runtime.
2. **Back up before every change** (timestamped, one copy inside the ESP + one in the workspace).
3. **Change one thing at a time**, Reset NVRAM after model/audio/RTC changes, then regression-test.
4. Validate syntax with `plutil -lint`; **deliver nothing that fails `ocvalidate`**.
5. After writing, `sync` → unmount → remount → verify SHA (FAT has write caching).
6. Move/delete a kext ⇒ set `Enabled=false` or delete the entry in the same pass.
7. Edit plists with `plutil`/`plistlib`, not hand-edited find-and-replace (`plutil -convert json` chokes on `<data>` blobs).
